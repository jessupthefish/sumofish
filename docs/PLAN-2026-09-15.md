# SumoFish plan, 2026-09-15: throughput, time, then the net

Written the morning after pondering went live. `STATE.md` session 16 has what
is deployed; this file is the order of work. Where it disagrees with
`PLAN-2026-08-14.md`, this one is newer, but read the old one's "Do not do
this" section, which still stands.

## What the live engine looks like right now

Measured 2026-09-15 on a live rapid game, fused 19M v7, pondering on:

- **~13.9k evals/s median** over the last 398 telemetry records.
- **The engine process sits at 100% of ONE CPU core while the GPU runs at
  ~68%.** The search is waiting on the host, not the card. The forward pass was
  89% of per-node cost when it was last profiled (before fusion and CUDA
  graphs), so that figure is stale and has to be re-measured.
- Moves search **~370-510k evals** in ~34 s budgets and inherit 0.5-3M visits
  from pondering. Tree cap: 25M nodes, `(tree)` stops on ~30% of ponders
  overnight (170 tree, 410 stopped, 3 cap).
- Rapid rating ~2659 over the night's games (W4 D3 L2 after the tree-cap
  fix). Far too few games to say anything about pondering.

One fact reshapes the priorities. The parity ladder's exchange rate falls from
1.15 node-doublings per sims-doubling at 200 sims to **0.49 at 1600->3200, and
live moves are ~7 doublings above that top rung.** Search is well into
diminishing returns at the operating point. So every "doubling of search is
worth X" number in this repository overstates what a doubling is worth live,
and judgment per node is worth relatively more live than the 3200-sim
break-even bar for a bigger net says.

## Where the strength is, ranked by expected gain per cost

1. **Throughput on the host side.** 32% of the GPU is idle because one Python
   thread feeds it. Candidates, to be chosen by profile, not by taste:
   pipelined evaluation (select the next batch while the GPU runs the current
   one, virtual loss already exists for exactly this), moving the per-batch
   Python glue (`tokenize_batch` -> numpy -> torch -> slicing -> lists) behind
   one Rust/pinned-buffer call, and pinned host memory for the H2D copy. Buys
   more own-clock search AND more ponder per second. No GPU-days. Caveat
   above: worth less per doubling live than the ladder says.
2. **Time allocation.** The engine spends 100% of its allowance on every
   move, including forced ones. Instamove and early stopping are built and
   were never priced; `match.py --tc` exists to price them. Pondering makes
   early stopping stronger than when it was built: time saved on a clear move
   is banked, and the tree it leaves is reused. Candidate third lever:
   extend time when the best move is unstable.
3. **Know what pondering is worth, and tune its cap.** Ponder on vs off, each
   against Stockfish on pinned CPU cores at a real clock (Stockfish must think
   on its own clock or there is nothing to ponder), then 25M vs 40M tree nodes.
   The lichess rating cannot resolve this.
4. **The 19M-fused-data net.** Trained, never gated. Session 15 expected zero
   to a small win. Cheap to settle and it has to be settled before anything
   is measured on top of v7.
5. **Search dials at the live budget.** `c_puct_init`/FPU were tuned at match
   budgets thousands of times smaller than a live move. Expensive to measure
   at a real clock; do it after 1-2 have moved the operating point again.
6. **A stronger net (the only jump, not an increment).** Width lost at
   matched tokens (2026-08-01 sweep); training depth is what won v7. Given the
   diminishing-returns fact, the break-even bar for a slower, better net is
   lower live than 0.79 node-doublings. Decide after 1-3, because they change
   how much search the bigger net would be giving up.

Not on the list: an opening book or local Syzygy (LAB-NOTES already records
why the tablebase is not free Elo; `online_egtb` is on), and anything aimed at
"fun to play against" (cancelled, PHILOSOPHY.md).

## Plan

### Phase 0: repairs and instruments (bot stays up, no GPU)

- [ ] **Threefold at the root returns no visits.** Twice on 09-15 the engine
      was asked to move in a position that was already a repetition, the core
      returned nothing, and `uci.py` fell back to the first legal move
      (`ValueError: no legal moves in ...`). Both games were drawn on that move,
      so it cost nothing yet. Fix: expand the root even when it is terminal by
      repetition, since the game is not over until someone claims it. Test with
      a position whose move stack repeats.
- [ ] **Retire `sumofish-train-fused-data.service`** (`mask`, or `disable`
      then re-link: `disable` deletes a linked unit's link).
- [ ] **Ponder summary script**: per game, share of opponent think covered,
      stop reasons, inherited visits per move, peak RSS. Reads `engine.jsonl`.
- [ ] **Re-profile one move on the real net** with the bot drained for ten
      minutes between games: py-spy on the engine plus `torch.profiler` around
      one `evaluate`. Output: where the one core's time goes. This picks
      Phase 2's design.

~6 cycles, GEN/VERIFY. Risk: the root-repetition fix touches the
identity-tested core, and `tests/identity_*` must still pass.

### Phase 1: one drained window (~12-14 GPU-h, bot down)

- [ ] `scripts/eval_heldout.py runs/19M-fused-data/best.pt`, clean subset.
- [ ] Clock gate vs v7 exactly as `pe2-gate` (`--time 0.5`, SPRT 0/20, fresh
      seed). Promote only on a pass; cut a version in the same sitting.
- [ ] Drain procedure: wait for no live game (`quit_after_all_games_finish`
      does NOT drain on SIGINT, see ~/CLAUDE.md), then stop.

~4 cycles of work, WAIT-dominated. Risk: SPRT runs long if the true
difference is near zero, which is the expected case.

### Phase 2: throughput (bot up; matches in short drained windows)

- [ ] Implement the design Phase 0's profile points at.
- [ ] Gate on **unique evals/s** (never raw nps, LAB-NOTES) on fixed
      positions, then a `--tc` match vs the current engine.
- [ ] Pipelining changes the search, so the identity tests stop applying to
      it; keep it behind a flag and keep the synchronous path as the oracle.

~13-20 cycles, VERIFY-dominated. Risk: pipelining plus the GIL plus PyO3's
`&mut self` borrow makes it a threading redesign; that roughly doubles it.

### Phase 3: time management and pondering, priced (~20 GPU-h, drained)

- [ ] `--tc` match: early stop on vs off, instamove on vs off, with pondering
      on in both arms (needs `match.py` to ponder; check before starting).
- [ ] Ponder on vs off against CPU Stockfish at a real clock, pinned cores.
- [ ] Tree cap 25M vs 40M, only if ponder is positive.

~8 cycles of work, WAIT-dominated. Risk: `match.py` has no ponder path, and
adding one is Phase 2-sized.

### Phase 4: decide the net bet

With Phases 1-3 done, restate the break-even bar at the live operating point
and decide: train depth on the fused d=384, or stop buying nets. Large,
40-70 GPU-h of WAIT if it goes ahead.

## Order and why

Phase 0 first because two items are bugs and the profile decides Phase 2.
Phase 1 next because every later measurement needs a settled net. Phase 2
before 3 because time management measured on a slower engine would be
re-measured afterwards. Phase 4 last because 1-3 move its bar.
